# PB-08: Multi-building operations

## Story and Status

An operator can onboard garages with independent layouts, gates and tariffs without building-specific application code (`ROADMAP.md`). The brief specifies only pilot `PB-AMS-2M8D`.

**Handoff draft, conditionally implementation-ready:** the approved product defaults and deterministic contracts below are intended for implementation, subject to the explicit cross-spec and migration blockers in Handoff Status. Vendor confirmation is a deployment prerequisite, not evidence of current support. This specification does not modify PB-03 through PB-06, authorize a commit or claim any implementation is complete.

## Scope and Decisions

- One ParkingBusiness organization, one admin credential, one provider account and one shared webhook HMAC secret. No multi-tenant authorization, refunds, automatic reconciliation, physical departure detection or new provider protocol.
- Building administration creates and reads buildings, adds and soft-removes spaces, sets tariffs, registers gates and activates a building. Existing resident administration remains available. No building deactivation, retirement or deletion; no gate deletion, reassignment or role change. No space number reuse, even after removal. No editing a space's floor or category: remove and add a different number.
- Building is `DRAFT` until explicit activation, then permanently `ACTIVE`. Drafts may be partially configured. Active buildings allow space additions/removals and tariff updates subject to the constraints below. Time zone is immutable after activation. The two required gates means at least one entrance and one exit, not two of each; the pilot retains its existing four.
- Each gate has one globally unique, immutable ID, building and role; secrets are deployment-managed, never issued by the API. One gate ID can have overlapping old/new credentials during rotation, but a credential cannot identify multiple gates or roles. Gate identity, not a caller-supplied building, determines access.
- Prices are EUR cents, positive per-hour rates and daily caps for visitor cars and motorcycles; residents are free. Use PB-04's elapsed started-hour blocks, local-date caps and 15-minute post-payment grace. A session snapshots its category, hourly rate, cap, currency and time zone at check-in; updates affect only later sessions. Never default a non-pilot building to pilot pricing.
- Preserve PB-03 eligibility, normalization, lowest eligible physical number and building-scoped registry and active-plate uniqueness. A plate may have active sessions in different buildings. A registered plate receives resident allocation regardless of button or vehicle; an unregistered resident claim fails; no visitor-category fallback. Release is on exit authorization, not physical departure.
- Soft removal retains space and historical foreign keys, excludes the space from allocation and public occupancy, and is rejected if occupied or if resident capacity would fall below registrations. Resident registration limit equals the count of non-removed resident spaces; this also applies to drafts. Existing pilot capacity remains 50.
- Signed-only webhook, session UUID routing and globally unique successful payment IDs across the single provider account. Payment never releases a space. No assumption that a rejected externally charged payment has been reversed.

## Sources and Conflicts

Read `BRIEF.md`, `docs/gates.md`, `docs/payment-provider.md`, `docs/architecture.md`, PB-03 through PB-06 and current implementation before implementation. The architecture's implementation status is stale; current schema contains building-scoped spaces and sessions, request bindings and checkout payment state, but fixed pilot gate configuration and pilot-specific flows remain. Existing code is not proof of reviewed or deployed behavior.

The PB-04 amendment committed in `63551c4` and PB-05 agree that a later payable checkout replaces the current amount; an earlier pending retry returns `409 CHECKOUT_SUPERSEDED` while active, with `EVENT_CLOSED` taking precedence after closure. Focused independent review found these rules in the committed implementation; it was not a comprehensive review of the amendment. This behavior does not solve attribution of delayed payments with equal amounts and no quote ID.

The brief's EUR 8.33 example conflicts with started-hour billing: PB-04 selects EUR 10 for 09:00 to 10:40. The provider requests unsigned legacy-terminal support while also requiring signatures; PB-05 deliberately rejects unsigned requests. Gate `402` handling, rechecks, `409` handling and correlation of late responses are not guaranteed by vendor notes.

## Admin API

All routes below use exactly one `Authorization: Bearer <admin-key>`. A missing or invalid credential is `401 UNAUTHORIZED`; a known non-admin credential is `403 FORBIDDEN`. Require JSON on body-bearing requests, reject unknown fields at every level and repeated scalar query parameters. Malformed JSON, invalid fields or unexpected body are `400 INVALID_REQUEST`; wrong media type is `415 UNSUPPORTED_MEDIA_TYPE`. Errors use `{"error":{"code":"CODE","message":"..."}}`, with sanitized messages. `503 SERVICE_UNAVAILABLE` covers unavailable database or bounded lock timeout; unexpected failures use `500 INTERNAL_ERROR`. Never return secrets. GET responses use `Cache-Control: no-store`.

Building codes are case-sensitive uppercase ASCII `[A-Z0-9-]`, length 1-64. Gate IDs are case-sensitive ASCII `[A-Za-z0-9-]`, length 1-64, globally unique; preserve pilot IDs `entrance-1`, `entrance-2`, `exit-1`, `exit-2`. A time zone must be a recognized IANA zone identifier, not a fixed UTC offset; persist the accepted identifier. Positive integer fields below are at most 2,147,483,647. Calculate monetary totals using checked arithmetic and fail closed rather than overflow the supported payment amount range.

| Operation | Request and success | Conflicts and missing resources |
| --- | --- | --- |
| `POST /admin/buildings` | Exactly `{"code":"PB-RTM-1","timeZone":"Europe/Amsterdam"}`. `201` returns `{"code":"PB-RTM-1","timeZone":"Europe/Amsterdam","status":"DRAFT"}`. | Existing code: `409 BUILDING_EXISTS`. |
| `GET /admin/buildings/{code}` | `200` returns `code`, `timeZone`, `status`, `spaces`, `tariff`, `gates` as defined below. Spaces and gates are sorted by number and ID respectively. | Unknown: `404 BUILDING_NOT_FOUND`. |
| `POST /admin/buildings/{code}/spaces` | Exactly `{"number":51,"floor":1,"category":"CAR"}`. Number is a positive integer; floor is an integer from -1000 through 1000; category is `RESIDENT`, `CAR` or `MOTOR`. `201` returns those fields. | Unknown building: `404 BUILDING_NOT_FOUND`; existing or previously removed number: `409 SPACE_NUMBER_USED`. |
| `DELETE /admin/buildings/{code}/spaces/{number}` | No body. Soft-remove a non-removed space; `204` empty. | Unknown building: `404 BUILDING_NOT_FOUND`; missing or already removed space: `404 SPACE_NOT_FOUND`; active session: `409 SPACE_OCCUPIED`; resident count would fall below registrations: `409 RESIDENT_CAPACITY_CONFLICT`. Occupied takes precedence. |
| `PUT /admin/buildings/{code}/tariff` | Exactly `{"currency":"EUR","car":{"hourlyRate":500,"dailyCap":3000},"motor":{"hourlyRate":300,"dailyCap":1800}}`; four amounts are positive integer cents. Atomically replace the complete tariff; `200` returns the submitted canonical object. | Unknown building: `404 BUILDING_NOT_FOUND`. No partial tariff or zero/negative values. |
| `POST /admin/buildings/{code}/gates` | Exactly `{"id":"rtm-entry-1","role":"ENTRANCE"}`; role is `ENTRANCE` or `EXIT`. `201` returns those fields. This creates association only, not credentials. | Unknown building: `404 BUILDING_NOT_FOUND`; any previously registered ID, including same building/role: `409 GATE_ID_USED`. |
| `POST /admin/buildings/{code}/activate` | No body; `200` returns the building representation. Requires at least one non-removed space, a complete valid tariff, at least one gate of each role, and registrations no greater than resident space count. Activation and validation are atomic. | Unknown: `404 BUILDING_NOT_FOUND`; already active: `409 BUILDING_ALREADY_ACTIVE`; missing prerequisites: `409 BUILDING_INCOMPLETE`. |

GET building `spaces` contains only non-removed `{number,floor,category}` objects; `tariff` is the complete object above or `null`; `gates` contains `{id,role}` objects. The API does not expose removed space history or credentials. There is no update-time-zone endpoint; correct a draft time zone through an explicit operator database procedure before activation, under stopped instances and with audit, or create a different building code. This is an operational exception, not an active-building mutation API.

For new admin routes authenticate first, then validate path, media type and body before looking up the building; after that apply the table's order. Invalid path numbers, codes and other malformed input give `400 INVALID_REQUEST`. Admin mutations do not use gate request IDs: duplicate creates conflict, repeated deletes return `404`, repeated activation returns `409`, and identical tariff PUT is safe to repeat. If a response or commit is uncertain, GET and reconcile before retry; an admin response must not assert rollback for an unknown commit. Log safe operation, building, outcome and time without credentials or plates; durable audit trail is not claimed.

Existing `POST /admin/residents`, `GET /admin/residents?buildingCode=...`, and `DELETE /admin/residents/{plate}?buildingCode=...` retain PB-03 fields, normalization, errors, ordering and no-store listing. Database building existence replaces the configuration allowlist: missing or unknown building still returns `400 INVALID_BUILDING` on these existing routes. Duplicate registration precedes `REGISTRY_FULL`; capacity is the number of non-removed resident spaces. Removal of a registration with an active resident session remains `409 RESIDENT_HAS_ACTIVE_SESSION`. Registry operations are allowed in draft and active buildings.

## Runtime Contracts

- `POST /check-in` keeps PB-03 body, response, validation, 1,500 ms budget and durable gate/operation/UUID request identity. Derive building from authenticated entrance gate; a known gate without a valid association or an inactive building cannot allocate: `409 BUILDING_INACTIVE` for draft, `503 SERVICE_UNAVAILABLE` for inconsistent/missing association. Match existing request conflict and replay precedence before mutable business conditions. Existing successful active retries replay; closed sessions return `409 EVENT_CLOSED`; business failures remain retryable under their bound canonical request. No building field is accepted.
- `POST /check-out` keeps PB-04 body, `200`/`402` shapes, role checks and request identity. A session unknown to the authenticated exit gate's building, including an existing session in another building, returns `404 SESSION_NOT_FOUND` without revealing ownership or mutating that session. After authentication and validation, bound-ID content conflict precedes session lookup; a matching committed success replays only for its original gate and building. Pending superseded checkout uses the aligned working-tree rule described above. Authorization, release and stored `200` are atomic and never release by space number alone.
- `POST /webhooks/payments` retains PB-05's exact raw-byte HMAC-SHA256 validation, payload, errors and ordering. Authenticate before parsing or session lookup; reject unsigned legacy calls. Resolve building only via the globally unique session UUID after signature validation. Successful payment ID uniqueness is global; identical validated success replays `204` even after closure, conflicting successful reuse returns `409 PAYMENT_ID_CONFLICT` before session lookup. Valid `FAILED` for a known session is logged and acknowledged without persistence, including when its ID matches a success. New successes must match the current outstanding amount on an active session; reject unexpected amounts or closed sessions as PB-05 specifies and log sanitized identifiers for manual investigation. Serialize global ID conflicts across buildings using a database unique constraint and transaction-safe conflict handling, not just building locks.
- Public `GET /occupancy/{building}` and `/availability` preserve PB-06 shapes, `no-store`, consistent snapshot, unknown `404` and known-empty `200`, for both draft and active buildings. Exclude removed spaces, and never expose plates, session IDs or payment details. Counts describe recorded availability, not physical presence.

## Pricing and State

Snapshot the full effective tariff, including time zone, in the same transaction as check-in. Resident snapshots explicitly indicate free eligibility; do not depend on later registry state. For visitors, charge each started elapsed hour anchored at check-in to the snapshot zone's local date at the block start, cap each date separately, and sum integer cents; zero elapsed costs zero and times before check-in fail safely. Midnight does not split a block, DST changes local date attribution but not elapsed duration. Preserve PB-04 minute-display rounding, grace start inclusive/end exclusive and valid-payment subtraction after expiry. A tariff change does not alter existing snapshots, outstanding amounts, payment history or replay responses. Persist zone identifier and deploy consistent time-zone database versions across instances; retain the version used for audit and document that future time-zone rule updates can change recalculation for long sessions unless historical rules are preserved. Do not claim full reproducibility across tzdb changes without that preservation.

The database is authoritative for buildings, spaces, gate associations and tariffs. Enforce building/number and gate ID uniqueness, immutable gate building/role, retained removed rows, session foreign keys, per-building partial unique active space and plate constraints, global session UUID and successful payment ID uniqueness. Reject invalid or missing snapshots instead of free exit. Enforce removal versus allocation and resident capacity under concurrency, including direct conflicting database writes where constraints can express the invariant.

Use compatible transactions across instances: take the building row lock before building-specific request, registry, space, session and checkout writes; serialize all operations that change resident capacity or eligibility with check-in, and serialize tariff update with snapshot creation. Payment ID uniqueness must additionally be resolved globally without reversing lock order or holding two building locks. Bound waits, handle deadlocks as retryable failures, and recover uncertain commits through durable request or payment identity. Keep bindings, including failed gate requests, and historic spaces, payments, sessions and authorization responses; monitor storage. Check-in allocation chooses the lowest eligible available number at its serialization point, not a higher number due to a skipped lock.

## Provisioning and Migration

Gate associations and deployment credentials require a coordinated stop/update/restart of **all** serving instances, not a rolling update. While stopped, register new associations using an isolated maintenance instance with external gate traffic blocked, then deploy the same complete credential mapping to all instances. Startup must validate configured gate ID/role against database associations, reject duplicate secrets, missing configured credentials for active gates and unknown or mismatched mappings, and fail closed on inconsistent instance configuration. Draft gates may be registered before their credentials exist; before activation, provision credentials and restart consistently. Activation verifies associations, not the physical gate or its secret. For rotation, deploy old and new secrets for the same ID/role together across the stopped fleet, restart, then repeat to remove old secrets. Use HTTPS and a separately provisioned admin secret; never store raw secrets in database records, API responses or logs.

Before cutover, inventory actual schema version, pilot and registry-only buildings, active sessions, request bindings, checkout quotes, successful payments, credentials and deployed instances. Back up and test restore; stop gate and provider traffic and all old instances, queue provider delivery safely, and reconcile in-flight/uncertain requests. Apply a transactional, versioned migration once, retaining all IDs and foreign keys; repeated migration/setup must not overwrite data. Seed pilot gate associations with the four existing IDs and roles, `Europe/Amsterdam`, car 500/3000 and motor 300/1800 cents, existing layout and active status. Backfill every active pilot session with the pilot snapshot according to its stored category; preserve check-in timestamps, active status, quotes, payments, grace timestamps, checkout and check-in request identities and exact replay responses. Preserve inactive history too; do not synthesize payment confirmations or change already issued amounts. Existing registry-only buildings stay draft; migrate their existing registration limits and records without silently discarding or inventing spaces. If registrations exceed their migrated resident-space count, block cutover for operator remediation, rather than deleting registrations or inventing capacity.

Validate snapshot completeness, referential integrity, unique IDs, gate roles, counts, pending quote/payment state and replay results before accepting traffic. Start identical new instances with credentials validated, test health and controlled pilot flows, then resume gate and signed provider traffic; monitor unexpected payments and reconcile externally. Migration failure before commit rolls back; if commit outcome is uncertain, inspect schema version and data before retry. After new traffic or configuration writes begin, do not simply restart old binaries: their pilot-only logic and schema assumptions can corrupt or reinterpret state. Rollback requires traffic stop, backup plus a reviewed restore/reconciliation plan accounting for all post-cutover sessions, payments and gate responses; if these cannot be reconciled, keep service stopped and recover forward. Validate this procedure in an isolated rehearsal before production.

- Test all pricing boundaries, both categories, zero duration, hour and midnight boundaries, caps, DST, grace expiry, tariff update while active with pending amount and recorded payment, checked overflow and tzdb/version handling. Assert pilot EUR 10 example and unchanged snapshots.

## Handoff Status and Blockers

1. **Cross-spec checkpoint:** focused independent review found the PB-04 amendment aligned with PB-05 and the committed implementation on replacement and closed-session precedence; the amendment landed in `63551c4`. The review was not comprehensive and did not independently run PostgreSQL integration tests; verify replacement and payment races against an isolated target. Future required spec checkpoints still need user authorization; no commit is authorized here.
2. **Migration implementation blocker:** inspect the actual deployed schema and data, including any non-pilot registry-only buildings and existing quotes, and resolve capacity conflicts without data loss. Pilot active sessions must remain usable; do not cut over with missing or ambiguous snapshots or replay state.
3. **Deployment blockers:** confirm gate `402`, rechecks, superseded `409`, event and late-response correlation and provisioning/rotation procedures with the gate vendor; confirm single-account payment ID uniqueness, signed delivery and operational handling with the provider. Upgrade or separately authenticate unsigned legacy terminals. The provider does not guarantee near-instant delivery; obtain an explicit operational risk acceptance or a changed integration for delayed/equal-amount ambiguous payments and external charges before deployment.
4. **Reproducibility blocker:** select and verify a way to preserve historical time-zone rules for active snapshots across tzdb updates, or obtain explicit acceptance of changed recalculation before deployment. A zone name alone does not freeze rules.

Implementation tasks: review this handoff and blockers; checkpoint any required specs with user authorization; implement schema and safe migration; implement admin and building-scoped runtime flows with database concurrency protection; document operations and execute the verification matrix with independent review. No application changes, vendor confirmations, tests or commits are implied by this draft.
